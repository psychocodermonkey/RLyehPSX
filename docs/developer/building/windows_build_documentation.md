# Windows build migration inventory

This inventory records build behavior from the former source-tree Visual Studio projects, filters, property sheets, resource scripts, and their helper batch files. The source-tree `.vcxproj`, `.vcxproj.filters`, `.props`, and `.aps` files were removed after this inventory was made; files under `dep/`, resource scripts, headers, and helper scripts were retained. Windows builds are currently unsupported. Use this record as a migration input when the dedicated CMake/Ninja Windows toolchain is implemented. It does not establish that the old projects built successfully. Compare each recorded setting with the then-current CMake configuration.

## Source of settings

- `dep/msvc/vsprops/Configurations.props`, `Toolkit.props`, `Base.props`, `BaseApplication.props`, `StaticLibrary.props`, `Win32Application.props`, and `ConsoleApplication.props` supply shared settings that are not visible in an individual `.vcxproj` file.
- `src/common/common.props`, `src/util/util.props`, and `src/core/core.props` add target settings. The Qt project also imports `dep/msvc/vsprops/QtCompile.props` and `QtCompile.targets`.
- The eight former source projects were `common`, `util`, `core`, `scmversion`, `duckstation-qt`, `updater`, `duckstation-regtest`, and `common-tests`. Their `.vcxproj` files defined build inputs and references. Their `.vcxproj.filters` files only organized those inputs in Visual Studio; they were not a separate source of compiler or linker flags. In particular, the Qt project's `CommonDataFiles` copy item was in the project but not its filters file. The two `duckstation*` filters files added no build inputs or settings beyond their matching project files.
- The repository has no active Visual Studio solution. The removed project files imported dependency `.vcxproj` files under `dep/`; check whether each required library is represented by a current CMake target or imported dependency.

## Target-specific inputs and links

- `common.props` supplies `src`, fast_float and fmt includes, `FMT_EXCEPTIONS=0`, and `OneCore.lib`. Current `src/common/CMakeLists.txt` already links `OneCore.lib` on Windows. `common.vcxproj` includes `fastjmp_x86.asm` for x86/x64 with `_M_X86_32` or `_M_X86_64`; `fastjmp_arm.asm` is limited to non-Clang ARM64 through the Visual Studio ARM assembler. Confirm the CMake assembler source and definitions for each supported architecture.
- `util.props` sets `CPUINFO_SHARED=1`, `ENABLE_VULKAN=1`, and `ENABLE_OPENGL=1` except on ARM64. `util.vcxproj` excludes the OpenGL context, device, pipeline, stream-buffer, and texture sources on ARM64, and references `glad.vcxproj` only on non-ARM64 platforms. The project excludes Unix/Apple-specific curl, EGL, and Metal inputs from Windows compilation. The property sheet adds Direct3D, DXGI, DWM, WinHTTP, and conditionally `opengl32.lib`; `WinPixEventRuntime.props` is imported for Debug configurations. It also names legacy dependency libraries and DLLs. Current CMake has Windows Direct3D and WinPix branches and uses SDL3, while the Visual Studio property file still names SDL2. Reconcile the target's features and dependencies with current sources rather than carrying over the SDL2 list.
- `core.props` sets `ENABLE_RAINTEGRATION=1` except on ARM64; `ENABLE_RECOMPILER=1` for x64/ARM/ARM64; `ENABLE_MMAP_FASTMEM=1` and `ENABLE_NEWREC=1` for x64/ARM64; plus `C4_NO_DEBUG_BREAK=1` and x64-only `XBYAK_NO_EXCEPTION=1`. It supplies architecture-specific raintegration, xbyak, and vixl includes. `core.vcxproj` selects the matching ARM32, ARM64, or x64 recompiler sources, excludes RISC-V64, and compiles `gpu_sw_rasterizer_avx2.cpp` only on x64 with AVX2 enabled. Its project references select `rainterface` off ARM64, `vixl` on ARM64, and `zydis` only for x64 Debug; the x64 Debug Zydis definitions/includes are also project-local. Compare these conditions with `src/core/CMakeLists.txt` before deleting the project.
- `duckstation-qt.vcxproj` imports `core.props`, so the application inherits its architecture-dependent definitions and includes in addition to `QT_NO_EXCEPTIONS=1`. It uses Qt's `Qt6EntryPoint` library and a Windows GUI subsystem; it disables warning 4127 (and Clang's ignored-pragmas warning). The Qt property sheet links Core, Gui, Widgets, and Concurrent and adds Qt's debug `d` suffix. Current CMake has a GUI subsystem and `QT_NO_EXCEPTIONS`, but its linked Qt target list and inherited definitions should be compared with the actual symbols used. The legacy executable naming comes from `BaseApplication.props`; use the intended R'Lyeh PSX output name instead of inheriting `duckstation-qt`.
- `updater.vcxproj` selects the Windows entry point, progress callback, resource script, and Qt runtime check; adds minizip includes plus `Comctl32.lib` and `zlibstatic.lib`; and uses the GUI subsystem. Current `src/updater/CMakeLists.txt` already models most of this but its runtime-check source path is stale (see below).
- `duckstation-regtest.vcxproj` compiles `regtest_host.cpp`, links the `common`, `core`, and `util` projects, imports `core.props` (including its architecture-dependent definitions and includes), and uses the console subsystem. Current `src/RLyehPSX-regtest/CMakeLists.txt` instead links `core`, `common`, and `scmversion`; compare the resulting transitive links and definitions rather than copying the old project references mechanically. `common-tests.vcxproj` is also a console target and includes googletest and `gtest_main.cc`. Preserve their source sets and test registration if these executables remain in the Windows scope.
- `scmversion.vcxproj` disables Visual Studio's fast up-to-date check and runs `gen_scmversion.bat` before build. That script obtains hash, branch, tag, and commit date from Git and rewrites `scmversion.cpp` when its signature changes. Current `src/scmversion/CMakeLists.txt` has a Windows generation branch; verify its working directory and rebuild behavior during migration.

The common, util, core, and Qt projects use `pch.h` as a forced include, with `pch.cpp` creating the precompiled header; the core AVX2 source opts out. Current CMake uses target precompiled headers, so compare exclusions where needed. Project references also define target ordering and static-library linkage; preserve those relationships through CMake targets rather than project GUIDs.

## Qt tools and runtime payload

`QtCompile.props` uses architecture-specific Qt trees but always takes host tools (`moc`, `uic`, `rcc`, `lrelease`, `lconvert`) from the x64 tree. It generates `moc_*.cpp` and `ui_*.h` into the intermediate directory, a binary `.rcc` in `bin/<platform>/resources`, and `.qm` files in `bin/<platform>/translations`. It copies Qt DLLs and plugins into `QtPlugins`, creates `qt.conf` with `Plugins = ./QtPlugins`, and merges/copies base Qt translations. The Qt `.vcxproj` explicitly lists MOC, UI, resource, and translation inputs; its `CommonDataFiles` item recursively copies `data/**` to the binary tree.

Current Qt CMake code already has resource and translation generation, `windeployqt`, `qt.conf.win`, and dependency-DLL copying. Compare the resulting runtime directory and required translations/plugins with the legacy payload. The legacy Qt project lists `resources/duckstation-qt.qrc` and `duckstation-qt_*.ts`; CMake uses renamed R'Lyeh PSX inputs. The old lists are historical, not a reason to reintroduce obsolete filenames.

## Windows resource metadata and versioning

`src/RLyehPSX-qt/duckstation-qt.rc` and `src/updater/updater.rc` embed the application/updater icon and `VS_VERSION_INFO`. Both declare English (Australia), code page 1252, and translation `0x0c09, 1200`; both set debug file flags under `_DEBUG`. The application records `RLyehPSX.exe` and a `0.0.0.0` numeric/string version; the updater records `updater.exe` and `1.0.0.0`. Each also carries `CompanyName`, description, product name, and copyright strings. Preserve the intentional metadata and attribution when moving to a generated or renamed `.rc` file; choose a real version source rather than assuming these placeholder values are current.

The Qt icon is `rlyehpsx-qt.ico` in its own directory. The updater resource still refers to it through the obsolete `..\\duckstation-qt\\` path. The existing `resource.h` comments now name `RLyehPSX-qt.rc` in both directories, but the files currently paired with those headers are `duckstation-qt.rc` and `updater.rc`. `src/scmversion/update_rc_version.bat` also targets the old `duckstation-qt` path and searches for version placeholders that do not match the current application `.rc`; treat it as an unverified legacy script.

## Known migration blockers and retirement check

- `src/RLyehPSX-qt/CMakeLists.txt` names `RLyehPSX-qt.rc`, which does not exist; the checked-in file is `duckstation-qt.rc`. Decide the final name, then align the CMake source, resource header, icon path, and any version-generation step.

- Legacy project files still use `duckstation-qt` names, SDL2 dependencies, and old translation/resource lists. Treat each as an inventory item to resolve, not as an authoritative specification for the new build.
- `.aps` was a Visual Studio resource-editor cache, and `.vcxproj.filters` stored IDE grouping. Neither contained unique compiler or linker parameters. Retain resource scripts, icon sources, and any useful metadata until their CMake replacements have been reviewed and Windows builds validated.
